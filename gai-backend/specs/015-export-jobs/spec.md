# Feature Specification: Export Jobs

## Scope summary

Export Jobs generates authenticated XLSX exports from project data. Jobs are
persisted and processed asynchronously by a database-backed in-process worker.
The worker atomically claims a `pending` row before generating a workbook and
stores the final bytes in the database, avoiding the current placeholder object
storage signer.

ZIP and CSV formats are outside this version. The supported types are:

- `inventory_items_xlsx`
- `inventory_accounting_items_xlsx`
- `pending_issues_xlsx`
- `payments_xlsx`
- `expenses_xlsx`
- `project_backup_xlsx`

## Tenant and project rules

- Every job belongs to one organization and one project.
- Organization users can only access jobs from their organization.
- Platform administrators can access jobs from any organization.
- Export creation is a read/snapshot operation and remains available for
  finished or otherwise operationally locked projects.
- Individual exports contain the current operational set and omit soft-deleted
  rows. For API compatibility, `project_backup_xlsx` names the consolidated
  project report: it includes the project, inventory, accounting, pending
  issues, payments, and expenses, including soft-deleted rows and their deletion
  timestamps. It is not a full physical backup of every project-related table.
- All sheets in one workbook are read through a single database transaction so
  a consolidated report observes one database snapshot.

## Lifecycle

- `pending -> processing -> finished`
- `processing -> failed` when generation fails
- `pending|processing -> cancelled` by an authorized user
- `finished -> expired` when retention elapses; expiration clears stored bytes
- `failed|cancelled|expired -> retry` creates a new pending job with
  `retry_of_id`; it does not mutate the terminal job
- Only one active (`pending` or `processing`) child retry is allowed for the
  same original job

The processor uses a conditional database update to claim a job. Final storage
also requires the row to remain `processing`, so a concurrent cancellation wins
and generated bytes are discarded. Stale processing jobs may be recovered after
the configured timeout. The worker limits concurrent generations
(`EXPORT_JOB_MAX_CONCURRENCY`, default `2`) and the rows loaded by a workbook
(`EXPORT_JOB_MAX_ROWS`, default `100000`) before serializing XLSX, avoiding
unbounded in-process memory growth. A periodic maintenance cycle expires
finished files even if no client lists or downloads them.

## API

Base path: `/projects/:projectId/export-jobs`.

- `POST /` requests a job
- `GET /` lists jobs with pagination and filters
- `GET /:jobId` returns job metadata
- `POST /:jobId/download-url` returns the protected API download path
- `GET /:jobId/download` streams the XLSX after authentication and authorization
- `POST /:jobId/cancel` cancels a pending/processing job
- `POST /:jobId/retry` creates a new job from a failed/cancelled/expired job

`download-url` is not a public presigned URL. Clients must send the bearer token
when calling the returned path. Public responses never expose file bytes,
storage paths, or bucket names.

## Listing

The list response uses `items`, `page`, `page_size`, `total_items`, and
`total_pages`. Filters: `type`, `status`, `requested_by_id`, `date_from`,
`date_to`, and `search`.

## Permissions

- `export-jobs:create`
- `export-jobs:read`
- `export-jobs:download`
- `export-jobs:cancel`
- `export-jobs:retry`

## Audit

Audited operations: request, start, finish, failure, cancellation, retry,
download URL creation, download, expiration, and stale-job recovery. Audit rows
store actor and state changes but never store file bytes or credentials.

## Errors

- `EXPORT_JOB_STATUS_TRANSITION_NOT_ALLOWED`: action is invalid for current status
- `EXPORT_JOB_CONCURRENT_MODIFICATION`: status changed during an update
- `EXPORT_JOB_ACTIVE_RETRY_EXISTS`: an active child retry already exists
- `EXPORT_FILE_NOT_READY`: job has no downloadable file yet
- `EXPORT_JOB_EXPIRED`: retention elapsed and bytes were removed
- `EXPORT_ROW_LIMIT_EXCEEDED`: workbook would exceed the configured row limit

## Implementation decision

The repository uses NestJS, TypeORM, manual MySQL migrations, and an SQLite
integration harness. The production migration uses `MEDIUMBLOB`; the entity uses
SQLite-compatible `blob` only in tests. The worker has no external queue
dependency and polls/claims persisted jobs atomically. The in-process worker is
appropriate for the current deployment; an external durable queue and object
storage remain the scale-out path for large installations.
