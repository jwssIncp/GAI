Migração das rotas do Laravel legado para o GAI · Contrato 1.0.0-rc.2 · Revisão 2, 10/11/2026 (URL oficial na AWS)

Este documento descreve, para a equipe do aplicativo Investor (Android/Flutter), todas as rotas que o app 1.4.6+1.12 usa no Laravel e a rota correspondente no GAI, com payloads, respostas, erros, permissões e o que muda no app. Ele pode ser lido sem acesso ao código do backend.

Estado: release candidate. Todas as rotas descritas aqui estão implementadas e cobertas por testes automatizados no backend (SQLite, MySQL 8 e storage S3 compatível, em ambiente local). A aplicação está publicada na AWS via CloudFront, e a URL base oficial é https://d1kanjou9wgm7q.cloudfront.net/api/v1. As rotas /mobile/* ainda não estão disponíveis nesse endereço (ver Ambientes), e a homologação do app contra a AWS continua pendente.

Observações sobre o ambiente

  • Health check: GET https://d1kanjou9wgm7q.cloudfront.net/api/v1/health → 200 {"status":"ok"}.
  • Rotas autenticadas sem token retornam 401 em JSON (ex.: GET /auth/me → {"code":"UNAUTHORIZED","message":"Authentication required"}).
  • Atenção: uma requisição para uma rota inexistente ou com método errado pode retornar 200 com HTML (a página do app) em vez de 404, por causa do fallback do CloudFront para a SPA. Se a resposta vier como text/html, revise a rota e o método. O app deve tratar qualquer resposta text/html da API como erro, nunca como sucesso.

Rotas /mobile/* ainda não publicadas (verificado em 10/11/2026). No endereço acima, /health, POST /auth/login e GET /auth/me respondem em JSON, mas GET /mobile/me, POST /mobile/auth/login e POST /mobile/auth/refresh devolvem 200 text/html (a página da SPA). O motivo é que o módulo mobile (gai-backend/src/modules/mobile) existe no código local, mas ainda não foi commitado nem implantado. Os caminhos documentados continuam corretos. Eles passam a funcionar nessa URL depois do próximo deploy que incluir o módulo. Até lá, o app não consegue usar o ambiente da AWS.

1.1 Regras de acesso comuns

Toda rota com Bearer passa pelas mesmas verificações, nesta ordem:

  1. Sessão válida e não expirada (senão 401 UNAUTHORIZED).
  2. Usuário ativo e organização ativa (senão 401).
  3. Senha temporária: enquanto must_change_password for true, só a troca de senha funciona; as rotas /mobile/... respondem 403 PASSWORD_CHANGE_REQUIRED. Senha temporária vencida: 401.
  4. Conta de campo: a conta precisa estar vinculada a um inventariante ativo. Sem isso: 403 MOBILE_ACCESS_DENIED.
  5. Projeto: nas rotas /mobile/projects/{projectId}/..., o inventariante precisa ter vínculo ativo e vigente com o projeto. Sem vínculo: 403 FORBIDDEN (ou PROJECT_NOT_AUTHORIZED). Projeto inexistente ou de outra organização tem a mesma resposta.
  6. Permissão: cada rota exige as permissões listadas (todas). Sem alguma: 403 FORBIDDEN (“Insufficient permissions”).
  7. Status do projeto: operações de escrita só em projetos draft, active ou paused. Fora disso: 409 PROJECT_STATUS_BLOCKS_OPERATION.

A organização e o inventariante vêm sempre da sessão. Nada que o app envie (ids de usuário, nome, organização) é usado como prova de identidade.

2. Autenticação e sessão

2.1 Modelo de sessão

ElementoValor
Access tokenOpaco (UUID). Vale 15 minutos e não é renovado pelo uso. Não tente decodificar; use access_token_expires_at.
Refresh tokenOpaco, formato gmr_ + 43 caracteres. Uso único e rotativo: cada refresh devolve um par novo. Vale 14 dias desde a última rotação.
Limite absolutosession_expires_at: 30 dias desde o login. Depois disso, só com novo login (o refresh responde 401 SESSION_EXPIRED).
Janela de duplicidadeSe o mesmo refresh token for usado de novo em até 30 s, a resposta é 409 REFRESH_TOKEN_ALREADY_ROTATED (requisição duplicada, não ataque).
Detecção de rouboReuso do refresh token depois de 30 s revoga a sessão inteira: 401 REFRESH_TOKEN_REUSED.
Bloqueio de conta5 senhas erradas seguidas bloqueiam a conta por 30 minutos: 423 ACCOUNT_LOCKED.
Inventariante bloqueadoLogin, refresh e demais rotas respondem 403 MOBILE_ACCESS_DENIED.

Diferenças em relação ao legado:

  • O campo email virou identifier e aceita e-mail ou login.
  • O token não é JWT. O app não pode mais conferir exp decodificando o token: deve usar access_token_expires_at.
  • O access token dura 15 minutos (antes 1 hora) e existe um refresh token separado.
  • A resposta não traz user.projects, user.email nem user.role. Os projetos vêm de GET /mobile/me.
  • user.name (usado como gai_user) deixou de ser necessário: o servidor identifica o técnico pela sessão.

O que muda no app:

  • Trocar o corpo para {identifier, password, device_label}.
  • Guardar access_token, refresh_token, access_token_expires_at e session_expires_at em armazenamento seguro (ver 2.8).
  • Se user.must_change_password for true, abrir a tela de troca de senha antes de qualquer outra chamada (2.6).
  • Depois do login, chamar GET /mobile/me para obter projetos e permissões.
  • Tratar 401, 403, 423 e 429 com mensagens distintas (o legado mostrava sempre “Não foi possível fazer o login”).

2.3 Refresh (renovação da sessão)

FuncionalidadeRenovar o access token sem pedir senha.
LegadoPOST /auth/refresh, sem corpo, com Authorization: Bearer <JWT vencido>
GAIPOST /mobile/auth/refresh
HeadersContent-Type: application/json. Sem Authorization.
PermissõesNenhuma; a conta e o inventariante precisam continuar ativos.

Requisição:

json
{ "refresh_token": "gmr_EXEMPLOexemploEXEMPLOexemploEXEMPLOexempl" }

refresh_token é obrigatório, com exatamente 47 caracteres no formato gmr_[A-Za-z0-9_-]{43}.

Resposta 200: mesmo formato do login, com um par novo (access e refresh). O access token anterior é revogado na hora.

StatuscodeAção no app
400VALIDATION_ERRORToken mal formado. Apague os tokens e peça login.
401INVALID_REFRESH_TOKEN, SESSION_EXPIRED, SESSION_REVOKED, REFRESH_TOKEN_REUSEDSessão encerrada. Apague os tokens e peça login. Não apague a fila offline.
403MOBILE_ACCESS_DENIEDInventariante bloqueado. Mostre “acesso suspenso”. Não apague a fila.
409REFRESH_TOKEN_ALREADY_ROTATEDOutra requisição do próprio app já renovou com esse token. Use o par que ela recebeu; se não houver, peça login.
423ACCOUNT_LOCKEDConta bloqueada temporariamente.
429TOO_MANY_REQUESTSAguarde e repita.

Diferenças em relação ao legado:

  • O token vencido não serve mais para renovar. Só o refresh token renova.
  • Cada refresh token funciona uma vez. Duas renovações paralelas com o mesmo token geram 409 na segunda.
  • Se o refresh falhar, o app não deve seguir com o token antigo: ele já não vale.

O que muda no app:

  • Renovar um pouco antes de access_token_expires_at (por exemplo, 60 s antes) ou ao receber 401 em qualquer rota.
  • Garantir um refresh por vez (mutex) e substituir os dois tokens a cada sucesso, gravando-os antes de liberar as requisições que esperavam.

FuncionalidadeEncerrar a sessão do aparelho (menu “Sair”).
LegadoNão existia (o app só apagava o JWT local).
GAIPOST /mobile/auth/logout
HeadersContent-Type: application/json. Sem Authorization.

2.8 Armazenamento seguro e tratamento de 401/403

  • Guarde os tokens com flutter_secure_storage (Android Keystore / EncryptedSharedPreferences). Nunca em SharedPreferences comum, banco local sem criptografia ou logs.
  • Não registre tokens, senhas ou URLs pré-assinadas nos logs de diagnóstico.
  • 401 em qualquer rota: renove uma vez e repita a requisição original uma vez. Se o refresh devolver 401, apague os tokens e vá para o login, mantendo a fila offline.
  • 403 não se resolve com refresh. Diferencie pelo code: PASSWORD_CHANGE_REQUIRED (troca), MOBILE_ACCESS_DENIED (acesso suspenso), FORBIDDEN em rota de projeto (vínculo encerrado: atualize /mobile/me e retire o projeto da tela; itens daquele projeto na fila ficam bloqueados até novo vínculo).

8.7 Sessões interrompidas

  • App fechado no meio: guarde session_uuid, file_id confirmados e o número/chave de cada lote. Ao voltar, consulte a sessão; reenvie os lotes não confirmados com a mesma idempotency_key (é seguro) e encerre.
  • Foto não confirmada a tempo (410): peça nova URL; o file_id antigo não deve ser usado.
  • Lote preso em processing (queda do servidor durante o processamento, por mais de 15 min): o finish responde 409 IMPORT_PAYLOAD_PROCESSING. O app não tem rota de reprocessamento: um gestor reprocessa pela web e o app reenvia o lote (idempotente) ou apenas encerra.
  • Sessão expirada (7 dias): abra uma sessão nova e reenvie.

9. Sincronização, conflitos e fila offline

9.1 Identificadores e idempotência

  • O id gerado no aparelho é a chave do item em todas as rotas e sempre texto. Zeros à esquerda são preservados. Ids numéricos do app não sofrem com a comparação sem distinção de maiúsculas usada pelo banco.
  • PUT de item, DELETE de item, confirmação de upload, criação de despesa (client_expense_id) e lote de reconciliação (idempotency_key) são idempotentes: repetir a mesma requisição depois de um timeout não duplica nada.
  • Itens criados por vários aparelhos ao mesmo tempo no mesmo projeto não colidem (validado com 4 aparelhos em paralelo no MySQL).

9.2 Versão do item

  • Cada item tem version, que aumenta a cada alteração (app, web, importação, fotos). As versões são únicas e crescentes por projeto.
  • Na edição, envie base_version = última version que o aparelho recebeu para aquele item (do PUT, do confirm-upload via item_version, ou da sincronização).

9.3 Conflitos 409

codeCausaRecuperação recomendada
VERSION_CONFLICTO item mudou no servidor (web ou outro técnico) depois da versão conhecidaLeia details.item. Se o técnico alterou campos que não mudaram no servidor, reaplique só esses campos sobre details.item e reenvie com base_version = details.item.version. Se os mesmos campos mudaram dos dois lados, mostre as duas versões e deixe o técnico escolher. Nunca force sem base_version atualizado.
ITEM_DELETEDO item foi excluído no servidorDescarte a edição local, marque o item como excluído e avise o técnico.
PROJECT_STATUS_BLOCKS_OPERATIONProjeto não aceita mais escritaErro definitivo; mova para “não enviados”.

Quando dois aparelhos enviam a mesma base_version, exatamente um recebe 200 e os outros recebem 409 (validado em teste de concorrência).

9.4 Fila de envio e política de tentativas

RespostaAção na fila
2xx (inclui 201, unchanged, already_deleted, already_confirmed, existing)Remove da fila e grava version/ids devolvidos.
404 ITEM_NOT_FOUND em DELETERemove da fila (concluído).
401Renova a sessão (uma vez) e repete. Se o refresh falhar, pausa a fila até novo login.
403Pausa as operações daquele projeto; atualiza /mobile/me. Não repete automaticamente.
409Move para a tela de conflitos (9.3). Não repete automaticamente.
410 (upload)Recomeça a foto do passo 1.
Outros 4xx (400, 404 de foto, 413)“Erro definitivo”, visível ao técnico, sem repetir.

Ordem: uma operação por item, na ordem em que foram feitas (criar → fotos → editar → excluir). Operações de itens diferentes podem seguir em paralelo (o app usa 2). A foto só sobe depois que o PUT do item foi concluído.

9.5 Exclusão offline

  1. O técnico exclui sem rede: marque o item como excluído localmente e enfileire DELETE.
  2. Se o item ainda tinha PUT pendente na fila (nunca enviado), cancele as duas operações.
  3. Ao voltar a rede, o DELETE responde 200 (deleted/already_deleted) ou 404 (nunca chegou): os dois são sucesso.
  4. A sincronização seguinte traz o item com deleted: true, confirmando o estado.
  5. Se outra pessoa editou o item antes, e o app enviou base_version, a resposta é 409 VERSION_CONFLICT: pergunte ao técnico se mantém a exclusão (reenvie com a versão nova ou sem base_version).

9.6 Alterações simultâneas (web e outros técnicos)

  • A sincronização por cursor traz todas as alterações, inclusive as da web, com a nova version.
  • Ao aplicar uma página, se o item local tiver edição pendente na fila, não sobrescreva a edição local: guarde a versão do servidor como base e deixe a fila resolver (o envio dará 200 ou 409).
  • Itens com external_item_id: null (web/legado) são somente leitura no app.

    return ApiError(

3.3 Refresh único (interceptor)

Requisitos: renovar antes de vencer ou ao receber 401; um refresh por vez; trocar os dois tokens; repetir a requisição original uma única vez.

class AuthInterceptor extends QueuedInterceptor {
  // `raw` é um Dio com as mesmas BaseOptions, SEM este interceptor: usado no refresh
  // e na repetição. Chamar o próprio `api` aqui dentro trava a fila do QueuedInterceptor.
  AuthInterceptor(this.raw, this.tokens);
  final Dio raw;
  final TokenStore tokens;
  Future<bool>? _refreshing; // compartilhado entre requisições concorrentes

  static const _public = ['/mobile/auth/login', '/mobile/auth/refresh', '/mobile/auth/logout'];

  @override
  Future<void> onRequest(RequestOptions o, RequestInterceptorHandler h) async {
    if (_public.contains(o.path)) return h.next(o);
    if (await tokens.accessExpiresWithin(const Duration(seconds: 60))) {
      await _refreshOnce();
    }
    o.headers['Authorization'] = 'Bearer ${await tokens.access()}';
    h.next(o);
  }

  @override
  Future<void> onResponse(Response r, ResponseInterceptorHandler h) async {
    final o = r.requestOptions;
    if (r.statusCode == 401 && !_public.contains(o.path) && o.extra['retried'] != true) {
      if (await _refreshOnce()) {
        o.extra['retried'] = true;
        o.headers['Authorization'] = 'Bearer ${await tokens.access()}';
        return h.resolve(await raw.fetch(o));
      }
      session.expired(); // vai ao login, mantém a fila
    }
    h.next(r);
  }

  Future<bool> _refreshOnce() => _refreshing ??= _doRefresh().whenComplete(() => _refreshing = null);

  Future<bool> _doRefresh() async {
    final refresh = await tokens.refresh();
    if (refresh == null) return false;
    final r = await raw.post('/mobile/auth/refresh', data: {'refresh_token': refresh});
    if (r.statusCode == 200) {
      await tokens.save(r.data); // grava ANTES de liberar as requisições em espera
      return true;
    }
    final e = ApiError.from(r);
    if (r.statusCode == 409 && e.code == 'REFRESH_TOKEN_ALREADY_ROTATED') {
      // Outro processo do app (ex.: WorkManager) renovou. Recarregue do storage.
      return await tokens.refresh() != refresh;
    }
    if (r.statusCode == 403) session.accessSuspended();
    if (r.statusCode == 401 || r.statusCode == 400) await tokens.clear();
    return false;
  }
}
  • Se o app tem sincronização em segundo plano (WorkManager/isolate), use um lock entre processos (por exemplo, arquivo de lock ou serializar todo acesso à API num único isolate). Dois processos renovando com o mesmo token geram 409 e, após 30 s, 401 REFRESH_TOKEN_REUSED (sessão revogada).
  • Antes de qualquer chamada, se session_expires_at já passou, vá direto ao login.

4.4 Conflitos

dart
Future<void> onConflict(int projectId, LocalItem local, ApiError e) async {
  final server = e.details?['item'] as Map<String, dynamic>?;
  if (e.code == 'ITEM_DELETED') {
    await db.markDeleted(local.externalId, reason: 'excluído no servidor');
    return queue.drop(local.externalId);
  }
  if (e.code == 'VERSION_CONFLICT' && server != null) {
    final changed = local.fieldsChangedSince(local.serverSnapshot); // o que o técnico mexeu
    final serverChanged = diff(local.serverSnapshot, server);       // o que mudou lá
    if (changed.keys.toSet().intersection(serverChanged.keys.toSet()).isEmpty) {
      // Sem colisão: reaplica só os campos do técnico sobre a versão nova.
      await queue.replacePut(local.externalId,
          body: {'base_version': server['version'], ...changed});
    } else {
      await conflicts.add(local, server); // tela para o técnico escolher
    }
  }
}

Guarde, por item, o último estado recebido do servidor (serverSnapshot) para calcular o que o técnico alterou. Nunca reenvie sem base_version atualizado.

5.2 Classificação das respostas

dart
SendResult classify(Response r) {
  final e = ApiError.from(r);
  switch (r.statusCode) {
    case 401: return SendResult.retryAfterRefresh; // o interceptor já tentou; pausa até login
    case 403: return SendResult.blocked;           // não repetir; ver 3.4
    case 409: return SendResult.conflict;          // tela de conflitos
    case 410: return SendResult.restartUpload;     // só uploads
    case 429: return SendResult.retryLater;
  }
  if ((r.statusCode ?? 0) >= 500) return SendResult.retryLater;
  return SendResult.failed; // 400/404 etc.: definitivo, visível ao técnico
}

Erros de rede e timeouts (DioExceptionType.connectionTimeout, receiveTimeout, connectionError) → retryLater.

5.3 Backoff

dart
Duration backoff(int attempt) {
  final base = Duration(seconds: 5 * (1 << attempt.clamp(0, 6))); // 5 s, 10 s, 20 s … 320 s
  final capped = base > const Duration(minutes: 5) ? const Duration(minutes: 5) : base;
  return capped + Duration(milliseconds: Random().nextInt(1000)); // jitter
}

Diferente de hoje, não repita para sempre erros 4xx: eles não se resolvem sozinhos.

5.4 Idempotência

Repetir após timeout é seguro para PUT de item (unchanged), DELETE (already_deleted), confirmações (already_confirmed), despesa com o mesmo client_expense_id (existing) e lote de reconciliação com a mesma idempotency_key. Gere essas chaves uma vez, ao criar a operação, e guarde-as na fila.

5.5 Migração da fila existente

Ao atualizar o app, itens pendentes do formato sync_items podem ser convertidos para put_item (criação sem base_version) + upload_image por foto ainda existente no aparelho. Como o PUT é idempotente, um item que já tinha chegado ao servidor pelo legado (mesmo id, mesmo projeto, se os dados foram migrados para o GAI) responderá 200 unchanged ou 409 (se divergiu). Exclusões locais nunca enviadas viram delete_item.

6. Sincronização por cursor

dart
Future<void> syncProject(int projectId) async {
  var cursor = await db.cursor(projectId); // null na primeira vez
  while (true) {
    final r = await api.get('/mobile/projects/$projectId/items/sync',
        queryParameters: {'limit': 200, if (cursor != null) 'cursor': cursor});
    if (r.statusCode == 400 && ApiError.from(r).code == 'INVALID_CURSOR') {
      cursor = null; await db.saveCursor(projectId, null); continue;
    }
    if (r.statusCode != 200) throw ApiError.from(r);
    await db.transaction(() async {
      for (final it in r.data['items']) {
        await db.mergeServerItem(projectId, it); // ver regras abaixo
      }
      await db.saveCursor(projectId, r.data['next_cursor']); // só depois de aplicar a página
    });
    cursor = r.data['next_cursor'];
    if (r.data['has_more'] != true) break;
  }
}

Regras de mergeServerItem:

  • Chave local: external_item_id. Se for null, use o id do servidor e marque somente leitura.
  • deleted == true → remova ou marque excluído localmente (e descarte operações pendentes desse item, exceto se quiser alertar o técnico).
  • Se houver operação pendente na fila para o item, não sobrescreva os campos locais: atualize só serverSnapshot (a fila resolverá com 200 ou 409).
  • Aplique apenas se version recebida for maior que a local.
  • images traz metadados das fotos do servidor; para exibir, peça GET …/images (URL de 300 s).

Quando rodar: ao abrir um projeto, após esvaziar a fila, periodicamente (por exemplo, a cada 5 min com o app aberto) e por ação do técnico. Substitui update_items e GET /external/.../items/sync.

Future<SendResult> uploadImage(int projectId, String externalId, File f) async {

  final imageId = r1.data['image']['id'];
  final headers = Map<String, dynamic>.from(r1.data['upload_headers']);

      data: Stream.fromIterable([bytes]),
      options: Options(headers: headers, validateStatus: (_) => true));
